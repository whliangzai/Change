# A股短线量化验证系统设计规格

## 目标

在既有 v1.1.0 基线文档和上位 PRD 的约束下，交付一个本地可运行、可测试、可部署的 Python 模块化单体，用于合法授权日线数据导入、历史股票池、强势趋势延续策略、含交易摩擦的回测、日报、人工确认计划和成交偏差复盘。系统只生成研究候选与人工确认清单，不提供自动下单、撤单、券商资金查询、自动补单或自动恢复风控状态。

## 设计决策

### 方案比较

1. **方案 A：模块化单体 + 并行 worktree（采用）**
   - 应用、Worker、数据库和队列通过一个 Python 项目交付，领域模块通过明确的 DTO、协议和状态机解耦。
   - foundation、data、engine、api、ops、tests 六个 worktree 分别开发，主协调分支按契约和实际 diff 集成。
   - 优点是满足并行开发要求，又避免微服务部署、跨服务事务和本地调试的额外复杂度。

2. **方案 B：先做单一端到端切片，再顺序扩展**
   - 先串通最小数据→信号→回测流程，再逐项补齐页面、运维和治理。
   - 风险是无法满足当前任务必须并行派发的要求，且基础接口晚确定会导致返工。

3. **方案 C：一开始拆成数据、策略、交易和报告微服务**
   - 每个服务独立部署，服务间使用 HTTP/消息队列通信。
   - 适合后续规模化，但首期会引入分布式事务、版本一致性和部署运维复杂度，偏离本地 MVP。

选用方案 A。并行边界只按目录与契约切分；共享契约先由 foundation 提供，所有跨模块写入都通过服务接口和数据库事务完成。

## 系统边界和组件

```text
浏览器/CLI
    │ X-Request-Id + Bearer Token
FastAPI API + Jinja2/HTMX
    │ 用例编排、RBAC、幂等、审计
领域模块
  数据与质量 → 历史股票池 → 信号 → 风控 → T+1 成交模拟 → 账本/报告
    │                         │
PostgreSQL 16/Alembic       Parquet 版本目录
    │
Redis 7 + RQ Worker（只执行研究、日报、备份任务）
```

- `app/core`：环境配置、日志、错误、认证、权限、请求上下文和风险提示。
- `app/domain/data`：数据批次、标准化行情、复权、交易日历、证券状态、行业历史和质量门禁。
- `app/domain/strategy`：按 `as_of_date` 和 `information_cutoff_at` 计算特征、资格、排除理由和稳定评分。
- `app/domain/risk`：现金、整数股、单票、行业、总投资比例、单笔风险和回撤状态机；不修改信号分数。
- `app/domain/execution`：读取 T+1 行情及规则，计算 `NEXT_OPEN_ADJUSTED` 参考成交价、费用和未成交原因；不创建信号。
- `app/domain/portfolio`：不可变订单、成交、账本、持仓和每日快照；成交与费用在同一事务中提交。
- `app/domain/backtest`：按时间顺序执行训练/验证/OOS 与滚动评估，绑定所有版本和内容哈希。
- `app/application`：导入、回测、日终、人工成交、偏差报告和导出用例。
- `app/infrastructure`：SQLAlchemy/Alembic、Parquet 存储、Redis/RQ、文件导入适配器和备份命令。
- `app/api` 与 `app/templates`：版本化 API、页面和统一错误呈现。

## 共享契约

### 版本和快照

所有数据批次、策略、成本、规则、回测运行、日报、计划和成交都带稳定 ID/版本；回测运行不可变地保存数据版本、策略版本、成本版本、规则版本、基准配置、时间切分、初始权益、参数快照和内容哈希。已发布策略、成本和规则只能复制成新版本。

### 时间隔离

信号计算的输入必须满足 `trade_date <= as_of_date` 且 `available_at <= information_cutoff_at`。买入计划的 `execution_date` 必须是 T+1 或之后；成交模拟只能读取执行日开盘和执行日规则，不能把 T 日收盘作为成交价。未来数据注入、当前存续列表替代历史股票池和未来行业/状态回填均由测试阻断。

### 状态和错误

数据批次、策略、回测、计划、风险和日报使用基线文档中的枚举及服务端状态机。业务错误统一为 `ValidationError`、`DataUnavailableError`、`RuleViolationError`、`StateConflictError`、`DependencyError`，API 映射到文档规定的错误结构和状态码。错误结果保留阶段、运行号、批次和可修复上下文，不生成伪完成报告。

### 金额、数量和费用

金额、价格和费率使用 `Decimal`，数据库使用定点 numeric；数量使用整数。主板买入数量按规则向下取整到 100 股，禁止负现金、负持仓、融资、杠杆和做空。默认成本为双向佣金 0.30‰、最低 5 元/笔、卖出印花税 0.50‰、双向过户费 0.01‰，并按 `commission_includes_*` 防止重复计提。

## 核心业务流程

1. 管理员创建授权 CSV/Parquet 数据源并导入批次，计算文件哈希，记录 `available_at` 和 `information_cutoff_at`。
2. 质量门禁检查缺失交易日、重复记录、非正价格、异常成交量、复权因子和历史状态；错误级问题将批次及其下游标为不可用。
3. 日终用历史状态按 T 日重建股票池，再计算市场开关、特征、资格、评分和排除原因。
4. 风控读取 T 日账户快照，应用 20,000 元初始权益、70% 最大投资、4 只持仓、单票 20%、行业 35%、单笔风险 1% 和 6%/8% 回撤状态，生成 T+1 计划。
5. 回测或模拟执行读取 T+1 开盘、停牌、涨跌停、缺价和交易规则，按 `FULL_OR_NONE` 产生成交或未成交结果，逐笔记录费用和原因。
6. 账本事务同时写入成交、费用、现金、持仓和快照；报告只读取不可变运行快照，展示策略、沪深 300、上证综指和股票池等权基准。
7. 人工确认和实际成交录入是独立动作；实际成交允许部分成交，原计划不可覆盖，差异和审计事件追加保存。

## 并行开发边界

| Worktree | 负责范围 | 共享输入 | 交付证据 |
|---|---|---|---|
| `foundation` | 项目骨架、配置、日志、认证、RBAC、审计、健康检查、共享异常/DTO | 基线文档、环境约束 | 启动检查、权限测试、文件清单 |
| `data` | SQLAlchemy 模型、Alembic、导入器、哈希、质量门禁、交易日历、历史状态和行情 | foundation 契约 | 迁移、夹具、数据质量测试 |
| `engine` | 股票池、基线策略、风控、成交模拟、账本、指标和回测编排 | foundation/data 模型 | 真实性测试、黄金回归、资金对账 |
| `api` | FastAPI 路由、Pydantic DTO、Jinja2/HTMX 页面、日报/计划/人工成交/导出 | foundation/data/engine 接口 | API、权限、端到端页面测试 |
| `ops` | Redis/RQ、幂等重试、Docker Compose、启动/导入/备份/恢复/监控命令 | app contracts | Compose 配置、任务测试、演练记录 |
| `tests` | pytest 夹具、契约、集成/API/安全/性能/回归检查、Ruff/mypy 配置 | 所有稳定接口 | 测试报告、追踪矩阵执行证据 |

子任务不得修改其他 worktree 的领域文件；共享接口变更必须先在契约目录中提交并通知所有依赖方。主协调分支负责解决集成冲突，不接受只凭口头汇报的完成结论。

## API 和页面设计

API 基础路径为 `/api/v1`。写操作强制 `X-Request-Id` 和 `Idempotency-Key`，访问 Token 30 分钟、刷新 Token 7 天；幂等结果保留 7 天，导出令牌 15 分钟且一次性使用。列表统一分页，金额/价格以字符串返回，资源权限检查在查询层和服务层双重执行。

首期实现登录、首页、数据质量、历史股票池、策略版本、回测创建/详情、日报/候选、计划确认、人工成交、持仓账本、报告导出、任务、权限、审计和告警页面。所有页面固定显示研究用途、不构成投资建议、不承诺收益、不自动下单；计划永远不表示券商委托或成交。

## 测试和发布策略

- 先用固定小型夹具验证业务不变量：历史退市/ST/停牌、复权变化、缺价、涨跌停、T+1、费用最低收费、部分成交、未来函数、幸存者偏差、现金/持仓对账和权限隔离。
- 每个 FR/NFR 映射到至少一个 `TC-*`；黄金数据集使用版本哈希，重复运行必须得到相同订单、净值和指标。
- 测试命令统一使用 `F:\PROJECT\Money.venv\Scripts\python.exe`，逐步执行 pytest、Ruff、mypy、迁移检查、健康检查和 Compose 演练。
- 本地 PostgreSQL 18.6 若用于开发，只验证与 PostgreSQL 16 的兼容 SQL/ORM，并在开发记录中标注版本偏差；发布 Compose 固定 PostgreSQL 16。
- 发布前必须关闭 P0：未来函数、账本不平、越权、自动下单路径、负现金/持仓和错误规则版本；通过备份恢复抽检后才启用日终任务。

## 验收边界

本设计覆盖基线文档要求的研究/回测/模拟盘/人工确认闭环；不扩展创业板、科创板、北交所、ETF、可转债、融资融券、杠杆、做空、自动下单、自动撤单、券商持仓/资金读取、自动补单或自动恢复。任何范围变化都必须产生新的需求、版本和测试追踪记录。
